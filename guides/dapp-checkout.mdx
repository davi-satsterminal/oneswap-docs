---
title: "Checkout"
description: "Let members pay for one experience in CC, your token, or both and deliver their purchase after your backend verifies a paid receipt."
---

Each checkout pays the verified creator wallet. The buyer sees the product price and a separate CC network fee before approving in OneSwap Wallet.

## Create a paid experience

In **My launches → dApps → Experiences**, choose an ID, a name and a pricing option. You can attach a holder requirement to any experience.

| Pricing | Availability |
| --- | --- |
| Free | A verified creator app |
| CC | Before or after your token graduates when CC checkout is enabled |
| Your token | When your graduated, migrated token supports checkout |
| Your token + CC | When mixed checkout is enabled and your treasury receives both assets directly |

For a mixed price, enter both amounts, for example **10,000 JOSE + 50 CC**. Use the receiving controls in the editor to authorize incoming assets if prompted. The buyer approves once. Both prices reach the treasury in the same ledger transaction, or neither settles. Deliver the purchased item from your backend after verifying the receipt. An edit to a price applies to new invoices. Existing invoices keep their original terms.

## Start an order

On an authenticated, same-origin purchase request, use the member’s server-side session. Check the capability for your price: `ccCheckout` for CC, `checkout` for the creator token, or `mixedCheckout` for both. Load the experience they can buy from your own catalog. Reserve a durable order ID before the first SDK call and reuse it for retries.

```js
const payment = await oneswap.payments.create(session.accessToken, {
  experienceId: order.experienceId,
  orderId: order.orderId,
})
if (payment.orderId !== order.orderId ||
    payment.subject !== session.subject ||
    payment.experienceId !== order.experienceId) {
  throw new Error('Could not match checkout to this order')
}
await orders.bindInvoiceOnce(order.orderId, {
  id: payment.id,
  orderId: order.orderId,
  subject: session.subject,
  experienceId: order.experienceId,
  legs: payment.legs,
})
```

Here, `orders` is your own database. Bind one invoice to the order atomically and reject a conflicting binding. Store each price leg with its kind, exact decimal amount, symbol and instrument (admin and ID). The fee is separate. If you already quoted a price on your site, compare it with the invoice before opening checkout. Send the browser only the saved payment ID.

```js
import { openCheckout } from '@oneswap/dapp-sdk/browser'

openCheckout(paymentId, 'devnet')
```

The buyer reviews the experience, amount, recipient and fee in their wallet and authorizes the payment. When a single-asset transfer produces an offer, the **creator as recipient** must accept it before expiry. A supported direct transfer can settle without that step. For a DevNet test, use a funded buyer account separate from the creator.

## Deliver only on a matching receipt

Fetch the merchant receipt from **your backend**. This call uses the app’s server credential and continues to work after the buyer’s session expires. Look up the order you saved when creating the invoice. Keep separate stores or keys for each app and network.

```js
import { isPaidReceiptFor } from '@oneswap/dapp-sdk/server'

export async function reconcileOrder(oneswap, orders, orderId) {
  const order = await orders.loadBoundInvoice(orderId)
  if (!order) return
  const receipt = await oneswap.payments.receipt(order.id)
  if (!isPaidReceiptFor(receipt, order)) return
  await orders.fulfillOnce(order.orderId)
}
```

The helper checks the paid status and receipt ID against the saved payment ID, order ID, subject, experience ID and complete list of price legs. A mixed checkout requires both exact instruments and amounts. Never accept those expected values from a browser callback. Implement `fulfillOnce` as a unique fulfillment record and entitlement in the same transaction. For an external delivery service, write a durable outbox record in that transaction and send the same fulfillment ID on retry.

| Wallet or receipt state | What your site should do |
| --- | --- |
| `open` | Let the buyer open the original checkout. |
| `approved` or `processing` | Show that payment is pending and recheck the same receipt. |
| `awaiting_acceptance` | Explain that the recipient must accept the transfer offer in their wallet. |
| `paid` | Verify the merchant receipt against the saved order and deliver once. |
| `declined` or `expired` | Keep the order unfulfilled. If the buyer chooses to try again, record a new payment attempt against the original purchase. |

A return to your site, wallet signature or polling timeout does not establish payment. For a status display you can use `payments.get(accessToken, paymentId)` or `payments.wait(accessToken, paymentId)`. On a timeout or service error, keep the current attempt and reconcile it. Never create another invoice just because the outcome is uncertain.

**DevNet check.** Buy a test pass, leave the wallet before delivery, then return to your site. Run reconciliation twice. Confirm that the member receives one pass, and only after a matching paid receipt.
